The decision log in five principles

DecisionPrinciple
IdentityThe normalised application number is the only key that crosses services. A person is a keyed hash of the national id. Service UUIDs are kept and measured, never joined on.
JoinsAs of commit time, against history, to one common cut-off. Orphans are kept, out of the denominator, and published to the team that wrote them. Every entity declares its grain and a test checks it.
GovernanceDirect identifiers never enter analyst-readable schemas. Every access is logged to a store the platform cannot alter. Regulatory retention overrides erasure.
RejectedHolding back rows until the sources agree. It ties every metric to the worst integration and changes the denominator. Instead: one owner per fact, every disagreement published with an owner, gated in aggregate.
To confirmWhether the decision service can emit an inputs snapshot keyed on application number and decision version. It lifts every Q2 answer to the top evidence grade.

Sixty seconds, one sentence per row. On the rejected trade-off, give the reason in full: it looks safe, but holding rows ties every metric to the worst integration, and it changes the denominator so the funnel stops reconciling to application counts. The runner-up confirm item is who mints customer_id, which branch applicants carry in the KYC and disbursement services but not in the application service. On identity, the risk I wrote down: the key assumes national_id holds one ID scheme, and the platform publishes two counts, ids collapsing into one key and same name-and-mobile under different keys, so the size of the problem is visible before anyone widens the use of personal data.
